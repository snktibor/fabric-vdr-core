# Concrete ledger refinement result

The concrete ledger model refines the existing skip protocol while preserving application state, every commit occurrence and persistent revoked history. Its atomic extension includes creation, plain and guarded updates, arbitrary extra-key reads and writes, and arbitrary state-preserving rejection. The full asynchronous no-bifurcation theorem transfers with independent check prefixes and arbitrary interleavings. Exact Java/JML-to-model and Fabric-to-model correspondence remain separate obligations.

The initial frozen contract has ten proved targets and one refuted target. A missing pair of parentheses made the first endorsement statement false outside update mode. The original remains sealed; a kernel-checked counterexample refutes it and a separately frozen corrected statement is proved. The [correction record](CORRECTION.md) gives the exact parsing issue and chronology. The atomic extension has eight further frozen targets. No original reconstruction file or original frozen model/spec was changed.

## What is established

- DONE: existing/absent records with signed integer versions; the invariant bounds existing versions to [0, 2^63-1]. Negative and exhausted update versions reject. `arithmetic` proves natural successor equality and the bound, and `Atomic.committed_update_exact` proves the actual committed target gets precisely its previous signed version plus one.
- DONE: creation at zero participates in the same run. Revision stability and actual-prefix snapshot provenance prove that committed creation sees a currently absent target, so it cannot reset an existing key. All plain and guarded registry writers are represented; there is no delete/reset transition.
- DONE: concrete endorsement tests target and guard existence, actual guard versions and checked successor availability. Target, guard and extra read revisions must match at validation. Application-counter equality alone never substitutes for revision equality.
- DONE: entry revisions and application counters are distinct. Same-revision/same-record stability is proved from concrete transitions, not assumed as a simulation premise.
- DONE: target plus nonce/other extra writes apply at one occurrence, each extra key once. Failed endorsement, any MVCC conflict or external rejection preserves all modeled state. Extra key values are opaque; their revisions are modeled explicitly.
- DONE: state, commit and revoked-history simulation for both the first model and the atomic extension. The allowance filter is computed from the concrete run. Its permitted occurrences are proved to satisfy abstract reads and produce the exact projected abstract update; no abstract-step correctness is a premise.
- DONE: full asynchronous no-bifurcation transfer, with arbitrary well-formed initial state, arbitrary initially revoked history, independently timed checks, different endorsement snapshots and arbitrary interleavings. There is no common fresh-check hypothesis.
- DONE: concrete witnesses cover creation followed by plain update, bounded arithmetic boundaries, self/repeated/missing/mismatching guards, stale target, extra-key conflict despite matching application reads, exact external skip, commit/revocation presence and absence, atomic nonce writes and distinct honest check prefixes.
- DONE: fresh Lean 4.23.0 compilation with `--trust=0`, exhaustive theorem/axiom audit, unchanged-dependency/frozen hashes, exact target inventory and source-only portable package. Relocated source-package replay and deliberate frozen-input corruption both behave as required; failure clears the stale success marker. The machine-readable [result](result.json), [inventory](theorem-inventory.json) and [portability evidence](artifacts/portability.json) are authoritative for the latest runs and counts.
- SEPARATE: exact Java service/caller/adapter correspondence, JVM/compiler behavior, deployed Fabric configuration and tuple-to-rank interpretation, authentication, issuer honesty, accumulator cryptography and faithful persistent-revocation interpretation.

## Implementation-facing witness

In `Witnesses.race`, the initial records at registry keys 0, 1 and 2 have application version 0 and accumulator payload 42. Their entry revisions are 100, 101 and 102, so they are visibly different quantities. At occurrence 0, an unrelated plain writer updates registry 2 to version 1/payload 53 and changes extra/nonce revision 10 in the same occurrence. Honest A checks B's registry at prefix 0; honest B checks A's registry at prefix 1. `check_registry_presence_and_provenance` proves both checked registries exist with the stated version and accumulator at those actual prefixes and in the endorsement snapshots. `honest_A` and `honest_B_later_check` prove the exact pinned guards and unrevoked-history conditions. A commits at occurrence 1 and B's stale reciprocal transaction rejects at occurrence 2.

The values 42, 51, 52 and 53 are opaque payload encodings, not computed accumulator proofs. Relating these witnessed checks to a real client requires that it checks the existing registry's actual accumulator and pins the version read from that same record, and that authentication and the intended payload effects are faithful. A version supplied independently of the checked accumulator is not justified by this artifact. Those provenance/faithfulness obligations are explicit; the theorem's abstract `HonestStep` was not changed to pretend to verify cryptography.

`extra_conflict_despite_matching_application_reads` shows the occurrence-0 atomic extra writer invalidating a later transaction while its target and guard application reads still match. `creation_zero_then_plain_one` uses a genuinely later endorsement snapshot to update a newly created key. These witnesses exercise the simulation premises rather than assuming an abstract execution.

## Trust and remaining correspondence

The complete boundary is in [CONTRACT.md](CONTRACT.md) and [ATOMIC-CONTRACT.md](ATOMIC-CONTRACT.md). Real Fabric revisions are block/transaction positions. The model uses their equality-preserving per-key history rank, fresh on every write, including extra keys. Snapshot provenance requires endorsement records to come from actual earlier ledger prefixes. The rank interpretation, atomic validation/rollback, ordering and provenance must be established for the actual platform. The parent's platform source audit targets [Fabric v2.5.15 commit 83c7930b3ea738eb2012da8316cfa8e749eac365](https://github.com/hyperledger/fabric/tree/83c7930b3ea738eb2012da8316cfa8e749eac365); that stated source target does not confirm the deployed peer version. This child artifact does not independently certify that platform audit or the deployment.

Java correspondence still needs key/credential decoding, target/guard reads and self-guard reuse, owner and nonce checks, complete read/write extraction, checked successor before mutation, one target put, creation/no bypass writers, snapshot provenance, atomic exception rollback, serialization/aliasing and event/JVM/compiler semantics. `source-audit.json` records the files read to choose these semantics. Source inspection and separately proved Java arithmetic do not automatically discharge these composition obligations.

All new proof dependencies must be a subset of `propext` and `Quot.sound`. The unchanged optional reconstruction prior-writer theorem retains its previously documented `Classical.choice`; the concrete safety chain does not use it. The runner rejects placeholders, custom axioms and untrusted compiled decisions. No production edit, global installation, commit or push was performed.
