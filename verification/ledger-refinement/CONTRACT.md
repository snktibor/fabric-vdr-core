# Concrete ledger semantic refinement

Frozen before proof search. This contract and `LedgerModel.lean` / `LedgerSpec.lean` are sealed in `frozen/semantic.sha256`. Existing reconstruction files are read-only dependencies; their baseline hashes are sealed separately. Only proof bodies, examples, audit tooling and reports may change after this freeze.

## Chosen scope

The concrete run includes creation, plain updates, guarded updates and arbitrary writes to extra ledger keys. Creation writes version zero to an absent registry key. Both update forms advance a nonnegative signed-long application version by exactly one, rejecting negative or exhausted values. A plain update is an update with an empty guard list. Every registry writer is represented, including unguarded writers to keys used by honest guards. There is no delete, reset, migration or out-of-band registry writer. A deployment with such a writer must prove that it fits these transitions or cannot affect the represented keys. Creation is included in the safety transfer: the projection of an absent key is zero, so creating it at zero stutters in the abstract application state. A theorem must prove that committed creation cannot overwrite an existing record.

The initial state is arbitrary subject to `WellFormed`: every existing record has a version in [0, 2^63-1]. Absence, accumulator values, application versions, entry revisions, extra revisions, initial revoked credentials and interleavings are otherwise arbitrary. In particular, revisions need not equal application versions and no initial pair freshness is assumed. Negative versions are representable and rejected by endorsement; preserving the initial well-formedness invariant is a separate target.

## Ledger and platform boundary

`Ledger` has optional records and separate natural-number revision ranks. Every accepted write advances the written key's rank; a record write also replaces its value. Extra keys have their own namespace and ranks. Real Fabric revisions are block/transaction positions, not application counters and not literally per-key successors. The explicit platform assumption is that these positions admit a per-key history rank preserving equality, with fresh ranks on every write and no ABA. The rank increment model is that quotient representation. Fabric ordering, MVCC, atomic rejection and this quotient are not proved from Fabric source.

A proposal stores an actual endorsement peer snapshot, its operation, target/call, new accumulator and arbitrary extra reads. `eligible` actually checks target existence (or absence for creation), all guard record existence and exact nonnegative application-version equality, and checked successor availability. A self-guard reads the same snapshot; duplicates are harmless. Successful endorsement includes target and guard revision snapshots, plus every listed extra-key read. The model does not impose the Java parser's stricter guard-list syntax; it overapproximates it.

`accepted` requires external permission, successful concrete endorsement and equality of every recorded entry/extra revision at validation. Application equality alone is insufficient. The permission stream is arbitrary, including state-dependent rejection and any authentication, policy, endorsement or validation rejection; false preserves all modeled state and never commits. Failure before submission is represented by a rejected occurrence. The model proves safety, not liveness or an exact reason/error ordering.

`Origins` requires each proposal's peer to equal some actual run prefix no later than that proposal's occurrence. It makes no assumption about abstract endorsement, simulation, abstract validation, or successor correctness. The proof must derive same-revision/same-record across arbitrary prefixes from the concrete transition rules, then use that fact to transfer actual reads and writes. Snapshot extraction from actual distributed endorsers remains a platform correspondence obligation. Checks and endorsements may be at different prefixes; two honest checks are independent.

## Projection, occurrences and revocation

Application-state projection maps existing signed versions to naturals and absence to zero. Update transactions project to the existing `endorsedTx` with the exact target and guard pins. Creation and extra-key writes project to write-free transactions retaining their IDs. No occurrence is removed or reordered. The abstract allowance is computed solely from concrete acceptance at each original occurrence. This deliberately retains all concrete rejection reasons, including stricter MVCC and extra-key conflicts. Establishing that every allowed occurrence passes abstract reads and performs precisely the projected abstract state change is a theorem, not a run premise. Commit equivalence is proved for every occurrence, including creation and extra-key writes.

Credential identities are the unchanged `(registry key, credential index)` pairs. `Effects` assigns intended revocations to operation IDs. Concrete revocation requires an update, the affected credential's registry equal to the target, and that assigned effect. Abstract revocation uses precisely the same ID/effect and written-key membership. Creation and extra writes revoke nothing. Repeated IDs are permitted but then share their effect interpretation. To interpret actual transactions, IDs must distinguish different intended effect assignments (for example an injective encoding of authenticated transaction identity). `RevWF` is proved for this interpretation.

The ledger stores an opaque accumulator payload. The faithful interpretation assumption is that the authenticated issuer's payload update realizes exactly these assigned revocations, valid checks agree with the persistent revoked history, and credentials/registry identifiers are correctly decoded. No theorem here validates accumulator cryptography, witnesses, key ownership, proof of possession, revocation-policy honesty, JWT verification, JSON canonicalization, timestamps, exception behavior, compiler/JVM execution or networking. Authentication/format failures may only contribute rejection; admitted calls and payload effects still need their stated authenticity/fidelity assumptions.

## Frozen targets

Exact types are in `LedgerSpec.lean`: `ArithmeticSpec`, `EndorsementSpec`, `CreationSpec`, `RevisionStabilitySpec`, `InvariantSpec`, `StateSimulationSpec`, `CommitSimulationSpec`, `RevocationSimulationSpec`, `RejectSpec`, `NoResetSpec`, `NoBifurcationSpec`. The last transfers the existing full asynchronous skip theorem at independent actual check prefixes, arbitrary initial states, arbitrary interleavings and arbitrary rejection. It retains distinct honest call IDs, each check before its own use, and no common-check shortcut.

Required nonvacuity evidence includes successful creation, successful plain and guarded bounded updates, MAX-1 success/MAX and negative rejection, missing/mismatching guard rejection, stale target revision rejection, extra-key conflict despite matching application guards, external rejection without state change, an honest committed revocation and an asynchronous race with distinct checks/unrelated writes. Fresh replay must compile all targets and dependencies with pinned Lean 4.23.0, enumerate theorem dependencies and reject placeholders, untrusted decision compilation and custom axioms. Existing model/proof bytes must remain identical.

## Separate Java/JML correspondence obligations

The source audit observes `createRevRegEntry`, `updateRevRegEntry`, `updateRevRegEntryIfGuardsUnchanged`, `readGuardedVersion`, `checkGuardUnchanged`, `requireOwnedEntry`, `applyAccumulatorUpdate`, `RevRegEntryVersion.next`, `BaseRegistry.get/exists/put` and `RevRegEntryRecord`. This is evidence for choosing semantics, not a source refinement proof. The exact remaining obligations are: (1) normalized namespace/key and credential identity mapping; (2) target existence, parent ownership/authentication, self-guard reuse and nonself guard reads; (3) guard comparison against the value actually read; (4) checked-long successor and mutation/write order with exactly one target put; (5) creation absence check/zero and no bypass/reset/delete writer; (6) all adapter reads included in the Fabric snapshot, including parent/auth extra keys; (7) snapshot provenance and atomic rollback of every rejection/exception, serialization and object aliasing; (8) Fabric revision equality and ordered validation to this rank model; (9) faithful accumulator/revocation interpretation and honest check pins; (10) Java/JVM/compiler/environment assumptions. Parent Java-service evidence may discharge parts separately, but this artifact never labels them proved merely because its semantic model passes.
