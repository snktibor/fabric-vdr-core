# Atomic registry and extra-key writes

This extension is separately frozen before extension proof search. The initial model and its proof statements remain byte-identical. Parent review identified that actual registry operations can atomically write nonce keys. The first model could only write extras in a separate `Mode.extra` occurrence, so it cannot directly represent that complete pointwise revision trace.

`AtomicModel.lean` adds an arbitrary finite `extraWrites` list to each transaction, in every mode. A successful occurrence applies its registry creation/update or primary extra-key operation and increments each listed extra revision exactly once at the same occurrence. If the primary extra target is also listed, it still increments once. Entries, entry revisions and all additional revisions change atomically; a rejected occurrence changes none of them. All extra reads retain exact revision-equality validation. A registry transaction that writes a nonce can therefore invalidate a later stale nonce reader at the correct occurrence.

Extra keys have opaque values: only their MVCC revisions are represented. Checks on nonce content, authentication and policy are represented by the arbitrary permission filter, whose accepted executions require separate implementation justification. The explicit platform rank/no-ABA, actual-prefix snapshot provenance and Java/JVM/Fabric/auth/accumulator assumptions in the original contract still apply. No source verification or nonce-policy theorem is inferred from this extension.

The eight exact target propositions in `AtomicSpec.lean` require the atomic write footprint, bounded-state invariant, no reset by creation, application-state simulation, pointwise commit simulation, persistent revoked-history simulation, exact state-preserving rejection and full asynchronous no-bifurcation transfer. Every represented registry writer still occurs; extra writes never excuse dropping a target writer. Initial states, checks, interleavings, additional read/write sets and rejection are arbitrary within the stated invariants. Snapshot provenance refers to this atomic run itself.

Required witnesses include a target update and nonce revision change at one occurrence, a later extra-read MVCC conflict despite matching target/guard application versions, and an honest reciprocal race with distinct check times. Existing core proof helpers may be reused only after proving the relevant equalities for the atomic semantics.
